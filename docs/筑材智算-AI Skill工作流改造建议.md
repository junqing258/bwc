# 筑材智算：AI Skill 工作流改造建议

日期：2026-10-27。性质：基于设计资料、原仓库代码和既有规划的评估建议；未修改原项目，未实现下述新能力。

后续已完成[现有 AI 工作流工具调研](AI工作流工具调研-2026-10-27.md)：Speckle 已有模型聊天与 Skills，Sparkel 已有算量 MCP 和交互预览，IfcOpenShell 已有官方 IfcMCP。因此本文所述工具层应优先评估复用，建议先验证现成产品和组件，再确定自建范围。

## 结论

可以直接以 AI Skill 工作流作为新的产品主线。推荐形态为“任务入口 + 可交互模型预览 + 关键问题卡 + 结果文件”，后台由一个 Agent 调用解析、查询、预览与计算工具。

需要区分两项改造：Skill 降低用户操作和业务流程的复杂度；解析进程、对象索引、分块显示和可恢复任务解决大型复杂项目的处理能力。两项需要配合建设。

对开发者，可先在支持 Skill 的 Agent 环境里调用本地工具验证；面向小白用户，应提供一个能直接打开文件的应用入口，封装运行环境、依赖和任务恢复。用户无需安装 Skill、启动服务或了解工具名称。

## 1. 原方案的问题在哪里

原设计的主流程从创建项目一路延伸到模型检查、构件确认、算量、预算、商品、询价和报价。四张设计稿分别呈现概览、四区算量工作台、预算配置和供应商比价。

这套布局适合熟悉算量流程的专业人员，但普通用户需要先理解楼层树、构件、材料规格、几何量、净工程量、采购量和费用口径，才能知道下一步做什么。直接增加聊天侧栏，仍然保留了较高的学习成本。

大型项目还有另一类问题：应计范围如何确定、异常如何分组、批量修改如何复核、长任务中断后如何继续。聊天界面本身无法解决这些问题。

代码核对结果：

| 环节 | 当前实际情况 | 改造含义 |
| --- | --- | --- |
| 文件解析 | `parse-model-file.ts` 在浏览器内解析 GLB/glTF、OBJ、FBX；IFC 明确未接入 | 可以复用小模型预览入口；正式解析需要适配器 |
| 容量 | 单文件最大 30MB，超过 100 万三角面拒绝；面数检查发生在完整解析后 | 删除阈值无法证明支持大项目，需要独立进程和容量验证 |
| 真实模型算量 | `attachModel` 创建空 `elements`，提示尚未生成工程量 | 必须补齐源对象、业务构件与计量项的关联 |
| 模型保存 | 业务对象保存到 localStorage；导入的 Three.js Group 在内存里 | 需要持久保存文件、解析产物和可恢复任务 |
| 模型联动 | `ModelViewer` 用 `userData.elementId` 关联选中与高亮 | 外部模型需建立对象映射，不能把演示联动视为已接通 |
| 既有规划 | `模型分析-Agent会话与人工校正方案.md` 已提出一个执行器、本地工具与人工校正，尚未实施 | 可沿用数据与变更契约，进一步收敛默认界面 |

## 2. 建议的用户体验

初始页面只有文件拖入区、最近任务，以及“预览模型”“检查问题”“生成材料清单”三个可选目标。用户可以点击目标，也可以直接说需求，无需先创建并填写完整项目。

一个典型流程：

1. 用户拖入文件，选择“检查并预览”。系统根据实际可用适配器读取文件，显示真实阶段；暂不支持的格式给出具体处理路径。
2. 系统生成可用的二维或三维预览、对象摘要和解析问题。二维图纸保持二维呈现，不凭空补成三维建筑。
3. 用户说“帮我算 A 栋一层楼板混凝土”。系统先查询并高亮候选范围，发现范围或计量依据不足时生成问题卡。
4. 用户处理问题卡，例如确认单位、指定计量范围、提供厚度依据。相同问题按确定范围分组处理，每组可查看成员并排除例外。
5. 系统调用确定性工具计算，结果区显示已计算小计、剩余缺项和对应构件；用户可追问、局部修改或导出。

默认任务界面建议：

```text
┌──────────────────────────────────────────────────────┐
│ 文件 / 当前任务     解析 → 预览 → 确认 → 结果         │
├─────────────────────────────────┬────────────────────┤
│                                 │ 任务进度与说明     │
│       二维 / 三维预览            │                    │
│       自动定位当前问题          │ 当前问题卡         │
│       支持点选与纠正            │ [查看范围] [处理]  │
│                                 │                    │
│                                 │ 输入目标或补充依据 │
├─────────────────────────────────┴────────────────────┤
│ 结果摘要 / 待处理问题        查看明细  导出  专业工具 │
└──────────────────────────────────────────────────────┘
```

构件树、完整属性表、复杂筛选和批量编辑保留在可展开的专业工具里。问题卡直接带入相关模型范围和输入表单，避免用户在多个页面之间寻找设置。

流程的可读阶段固定；Agent 可以在阶段内选择工具、反复查询和修正。执行进度来自工具事件，完成状态由运行时检查实际产物和校验结果后确认。

## 3. Skill、Agent 和工具的分工

Agent Skills 标准允许将指令、脚本、资料和模板打包为可按需加载的目录。因此适合封装业务处理方法；项目状态、运行时、几何内核和交互预览仍由应用及工具承担。[Agent Skills 官方概述](https://agentskills.io/home)

建议先做一个总入口 Skill：`building-model-workflow`。按需加载解析、预览、问题处理和算量资料，工具单独版本化；等流程稳定后，再拆为可独立复用的技能。

| 层次 | 负责什么 | 建议边界 |
| --- | --- | --- |
| Skill | 处理步骤、问题分组方法、格式分支、何时补资料、结果要求 | 不保存项目唯一状态；不以提示词代替计量规则 |
| Agent | 理解目标、查对象、组织问题、选择工具、解释结果 | 使用分页查询和摘要，不把整栋模型逐对象塞进上下文 |
| 任务运行时 | 调用工具、参数校验、取消、重试、检查点和阶段推进 | 依据实际工具返回判断成功，保留部分失败 |
| 领域工具 | 解析、索引、几何检查、计量、参数变更、导出 | 有结构化输入输出与明确的支持范围 |
| 预览器 | 二维/三维显示、定位、高亮、选择、剖切、显示状态 | 通过对象 ID 与业务状态联动；截图只是辅助证据 |
| 项目存储 | 原文件、解析产物、人工依据、变更记录、结果快照 | 独立于聊天记录持久化 |

建议的工具契约示意，名称与接口均为待实现：

| 工具 | 输入重点 | 输出重点 |
| --- | --- | --- |
| `inspect_file` | 文件引用、处理目标 | 格式、适配器支持、依赖和限制 |
| `parse_model` | 文件版本、解析配置 | 任务 ID、对象索引引用、完整性、未解析范围 |
| `query_elements` | 模型版本、筛选、分页 | 对象摘要、来源和对象引用 |
| `build_preview` | 解析产物、分块策略 | 显示产物与对象映射 |
| `set_view` | 预览会话、冻结选择集 | 实际定位/高亮结果 |
| `diagnose` | 明确范围、可用检查项 | 问题组、证据和未执行检查 |
| `propose_change` | 范围、字段、值与依据 | 变更集、前后差异、试算结果 |
| `apply_change` | 变更版本、用户指令依据 | 新修订或冲突，支持受限撤销 |
| `calculate_takeoff` | 计量项、方法与规则版本 | 有效数量、公式、缺项与覆盖范围 |
| `export_result` | 冻结结果版本、输出范围 | 清单、问题与依据文件 |

预览联动可以使用本地接口或事件通道；接入支持 MCP 的外部 Agent 时再提供 MCP 适配。是否采用 MCP 不改变底层工具的数据契约。

## 4. 大型复杂项目需要补哪些能力

以下是建议建设项，并非原项目已实现能力。

- 建立项目级文件清单，容纳多楼栋、多专业、多文件，并保留源坐标、单位和跨文件定位变换。
- 解析放进可取消的独立进程。按适配器能力尽早产出对象索引和局部预览；无法渐进解析的格式仍需明确其完整读取成本。
- 预览按楼栋、楼层或空间分块加载，支持实例复用和显示细节分级。计量继续引用独立保存的计算几何与方法，显示抽稀不改变工程量。
- AI 通过索引查询与汇总定位问题，只读取当前任务相关数据。异常按原因和影响范围分组，避免逐构件问答。
- 保存任务检查点，缓存按文件指纹、解析器版本和配置判定有效。刷新、服务重启或 AI 超时后可以恢复；跨版本对象映射需要校验。
- 分类、厚度、规则发生变化后，按依赖失效并重算受影响结果；依赖不明确时扩大失效范围，防止沿用旧值。
- 记录部分解析和未知失败范围。不能仅凭已解析对象都已完成，就把整个项目标成完整。

例如 IFC 路径可评估 IfcOpenShell 的几何迭代器，官方提供多核处理、缓存和复用能力；这只是可用机制，仍需目标文件与设备验证容量。[IfcOpenShell 几何处理文档](https://docs.ifcopenshell.org/ifcopenshell-python/geometry_processing.html#geometry-iterator)

大型模型处理能力和大型项目协同能力分开建设。第一版可验证单机处理较大模型；权限、多人协同、供应商和交易属于另外的产品范围。

## 5. 解析和预览先做到什么程度

支持矩阵至少区分“读到记录、可显示、可测量、可业务算量”四个层次。

| 输入 | 第一轮建议 | 现有证据与限制 |
| --- | --- | --- |
| DWG / DXF | 若首批用户主要提供图纸，优先打通对象索引、二维预览、单位校准和目标轮廓测量 | 原仓库已有 ACadSharp / ezdxf 样本探针；尚未证明完整显示、面积及三维实体计算 |
| GLB / glTF | 复用现有预览，增加持久保存、稳定对象映射与诊断 | 能显示不代表有建筑语义或可用净体积 |
| IFC | 若真实任务有 IFC，单独验证语义与几何适配 | 当前前端明确未接入；不因其语义较丰富就假定数量属性可信 |
| OBJ / FBX | 保留已具备的预览路径，按样本验证业务可计算范围 | 材料、单位、实例与外部资源需单独处理 |
| MAX | 沿用明确的导出指引，待转换能力真实接通后再开放 | Skill 不增加原生格式的解析能力 |

第一轮只选择一种真实主格式走通闭环。DWG 与 IFC 不因规划里都出现就同时建设；依据真实来件与验收任务决定先后。

## 6. 实施顺序

**第一步：建立可独立调用的工具闭环。** 从真实文件得到对象索引、可交互预览、诊断文件和可恢复项目目录；先验证不接 AI 时也能运行。复用现有前端与探针，隔离演示数据，补齐真实数据契约。

**第二步：接入一个 Agent 和总入口 Skill。** 用户说“打开并检查这个文件”，Agent 自动调用读取、解析、预览和诊断工具。先交付模型解析与预览这条完整路径，计量仍按已验证的方法开放。

**第三步：加入一种真实算量任务。** 可选择水平楼板范围确认、面积依据、均匀厚度补录到混凝土清单；具体任务由首批来件决定。人工与 AI 共用同一参数变更和计算入口。

**第四步：用大型真实样本和小白用户检验。** 记录解析峰值内存、首次可用预览耗时、交互表现、中断恢复和实际未解析范围；观察用户能否从打开文件一路完成任务。再补分块、索引与问题分组中暴露的瓶颈。

对第一版应用，近期任务、预览、问题处理和结果导出已足以形成主界面。预算、供应商比价、团队设置和交易能力按后续真实需要接入。

## 7. 不能因界面简化而丢失的约束

AI 可以提出分类和材料建议；工程量由可验证的几何、规则和已采用参数生成。外观或名称不足以确定单位、混凝土等级或厚度。

明确指令可以直接形成可撤销的工作副本修改；范围或参数不明确时，问题卡展示候选与依据。避免对每次查询反复确认，同时保留人工复核状态。

缺参数、缺价格与有效零值分别保存。部分结果允许导出，但必须标明范围、未解析部分和待处理项。每条结果可回到文件版本、对象或面集、计量方法和人工依据。
